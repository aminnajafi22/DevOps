سناریوی عملی مدیریت پاد و فضای نام

دو محیط مستقل برای توسعه و عملیات بساز؛ دو وب‌سرور با نام یکسان اجرا کن و از یک پاد آزمایشی به هر دو متصل شو. در این پروژه فقط از منابع Pod و Namespace استفاده می‌شود.

خروجی نهایی: دو صفحه وب متفاوت، یک کلاینت آزمایشی، مدیریت منابع، ارتباط مستقیم بین پادها و یک آزمون حذف و بازیابی.

PART 01 / TASKS

مراحل تمرین — بخش اول

ابتدا تلاش کن همه مراحل را بدون دیدن پاسخ‌ها انجام بدهی. هدف، فهم رفتار خود پادها و فضای نام است؛ نه حفظ کردن YAML.

1

بررسی سلامت کلاستر

نودهای کلاستر را مشاهده کن. وضعیت، نام و IP آن‌ها را بررسی کن؛ همه نودهای موردنیاز باید آماده باشند.

معیار قبولی: بتوانی Master و Workerها را شناسایی کنی.
2

ساخت دو Namespace

دو فضای نام lab-dev و lab-prod بساز. وضعیت هر دو باید Active باشد.

معیار قبولی: دو Namespace مستقل در فهرست وجود دارند.
3

پاد وب محیط توسعه

در فضای توسعه، پاد web با یک کانتینر Nginx بساز؛ پورت ۸۰ و برچسب‌های app=web و env=dev داشته باشد.

معیار قبولی: پاد اجرا می‌شود و یک کانتینر دارد.
4

پاد وب محیط عملیاتی

در فضای عملیاتی نیز یک پاد با همان نام web و یک کانتینر Nginx بساز؛ برچسب env=prod داشته باشد.

معیار قبولی: دو پاد همنام در دو Namespace متفاوت بدون تداخل وجود دارند.
5

درخواست و محدودیت منابع

برای هر پاد وب: درخواست CPU برابر ۵۰ میلی‌کور، محدودیت CPU برابر ۲۵۰ میلی‌کور، درخواست حافظه ۶۴Mi و محدودیت حافظه ۱۲۸Mi قرار بده.

معیار قبولی: با مشاهده جزئیات پاد، مقادیر Requests و Limits درست هستند.
PART 01 / TASKS

مراحل تمرین — بخش دوم

6

ساخت پاد ابزار آزمایش

در lab-dev پاد toolbox با ایمیج BusyBox بساز؛ کانتینر باید برای ورود و آزمایش فعال بماند.

معیار قبولی: وارد Shell کانتینر می‌شوی و پاد به‌صورت عادی Running است.
7

تغییر صفحه هر وب‌سرور

با اجرای دستور داخل کانتینر، محتوای صفحه اصلی Nginx را تغییر بده: توسعه DEV ENVIRONMENT و عملیات PRODUCTION ENVIRONMENT را نشان دهد.

معیار قبولی: دو پاد پاسخ‌های متفاوت دارند.
8

تست ارتباط بین Namespaceها

IP هر پاد وب را پیدا کن. از داخل پاد toolbox ابتدا به وب‌سرور توسعه و سپس به وب‌سرور عملیاتی درخواست HTTP بفرست.

معیار قبولی: بدون Kubernetes Service و فقط با Pod IP هر دو پاسخ را دریافت می‌کنی.
9

حذف و بازیابی دستی

پاد وب توسعه را حذف کن. ببین آیا خودش برمی‌گردد. بعد همان پاد را دوباره از Manifest ایجاد کن و اتصال را آزمایش کن.

معیار قبولی: توضیح بدهی چرا پاد معمولی برخلاف Deployment خودکار بازسازی نمی‌شود.
10

پاک‌سازی انتخابی محیط توسعه

کل Namespace توسعه را حذف کن. بررسی کن پادهای آن حذف شده‌اند اما وب‌سرور محیط عملیاتی سالم مانده است.

معیار قبولی: Namespace عملیاتی و پاد آن بدون تغییر باقی می‌مانند.
مرز سناریو: تنها منابع موردنیاز Namespace و Pod هستند. ابزارهای خط فرمان برای ورود به پاد، ویرایش فایل و آزمایش HTTP مجازند. هیچ Service، Deployment، Ingress یا ConfigMap نساز.
PART 02 / ANSWER KEY

پاسخ منیفست‌ها — بخش اول

سه فایل زیر پاسخ کامل تعریف منابع هستند. فایل‌ها را به همان ترتیب اجرا کن. فایل اول دو Namespace و فایل دوم پاد وب توسعه را ایجاد می‌کند.

01-namespaces.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: lab-dev
  labels:
    environment: development
---
apiVersion: v1
kind: Namespace
metadata:
  name: lab-prod
  labels:
    environment: production
02-dev-web.yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: lab-dev
  labels:
    app: web
    env: dev
spec:
  containers:
    - name: nginx
      image: nginx:stable
      ports:
        - containerPort: 80
      resources:
        requests:
          cpu: "50m"
          memory: "64Mi"
        limits:
          cpu: "250m"
          memory: "128Mi"
چرا هر دو پاد می‌توانند web نام داشته باشند؟ چون یکتایی نام Pod در محدوده همان Namespace سنجیده می‌شود، نه در کل کلاستر.
PART 02 / ANSWER KEY

پاسخ منیفست‌ها — بخش دوم

فایل سوم پاد وب محیط عملیاتی و فایل چهارم پاد ابزار آزمایش را می‌سازد.

03-prod-web.yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: lab-prod
  labels:
    app: web
    env: prod
spec:
  containers:
    - name: nginx
      image: nginx:stable
      ports:
        - containerPort: 80
      resources:
        requests:
          cpu: "50m"
          memory: "64Mi"
        limits:
          cpu: "250m"
          memory: "128Mi"
04-dev-toolbox.yaml
apiVersion: v1
kind: Pod
metadata:
  name: toolbox
  namespace: lab-dev
  labels:
    app: toolbox
    env: dev
spec:
  containers:
    - name: busybox
      image: busybox:1.36
      command:
        - /bin/sh
        - -c
        - "while true; do sleep 3600; done"
در BusyBox یک فرمان خواب تکرارشونده گذاشته‌ایم تا پردازش اصلی کانتینر فوراً تمام نشود و بتوانیم با kubectl exec وارد آن شویم.
PART 03 / VERIFY & EXPLAIN

پاسخ اجرایی — ساخت و بررسی

۱. ایجاد منابع

kubectl apply -f 01-namespaces.yaml
kubectl apply -f 02-dev-web.yaml
kubectl apply -f 03-prod-web.yaml
kubectl apply -f 04-dev-toolbox.yaml

۲. بررسی Namespaceها و پادها

kubectl get namespaces
kubectl get pods -n lab-dev -o wide
kubectl get pods -n lab-prod -o wide
kubectl describe pod web -n lab-dev

۳. تغییر محتوای صفحه توسعه و عملیات

kubectl exec -n lab-dev web -- sh -c \
  'echo "DEV ENVIRONMENT" > /usr/share/nginx/html/index.html'

kubectl exec -n lab-prod web -- sh -c \
  'echo "PRODUCTION ENVIRONMENT" > /usr/share/nginx/html/index.html'

۴. مشاهده آدرس‌های واقعی پادهای وب

kubectl get pod web -n lab-dev -o wide
kubectl get pod web -n lab-prod -o wide

۵. ورود به پاد ابزار آزمایش

kubectl exec -it -n lab-dev toolbox -- /bin/sh

آدرس‌های فرضی زیر را با IP واقعی هر پاد جایگزین کن. دو دستور را داخل BusyBox اجرا کن:

wget -qO- http://<DEV_POD_IP>:80
wget -qO- http://<PROD_POD_IP>:80
پاسخ موفق ارتباط میان Namespaceها را نشان می‌دهد؛ خود Namespace به‌تنهایی جداسازی شبکه یا محدودیت دسترسی ایجاد نمی‌کند.
PART 03 / VERIFY & EXPLAIN

پاسخ اجرایی — خرابی، بازیابی و نتیجه

۶. حذف عمدی پاد وب توسعه

kubectl delete pod web -n lab-dev
kubectl get pods -n lab-dev

انتظار: پاد web از فهرست حذف می‌شود و به‌صورت خودکار برنمی‌گردد؛ چون هیچ کنترلری برای بازسازی آن تعریف نکرده‌ایم.

۷. بازیابی پاد از فایل Manifest

kubectl apply -f 02-dev-web.yaml
kubectl get pod web -n lab-dev -o wide

با ایجاد مجدد پاد، احتمالاً آدرس IP تغییر می‌کند. همچنین تغییر دستی صفحه HTML از بین رفته است، چون در فایل‌سیستم گذرای کانتینر انجام شده بود. برای تکرار آزمایش باید دوباره صفحه را تغییر بدهی.

۸. پاک‌سازی فقط محیط توسعه

kubectl delete namespace lab-dev
kubectl get namespaces
kubectl get pods -n lab-prod

انتظار: منابع داخل Namespace توسعه حذف شوند و پاد وب محیط عملیاتی باقی بماند.

چک‌لیست پایان سناریو

دو Namespace مستقل ایجاد شدند.
دو پاد با نام یکسان، ولی در Namespaceهای متفاوت اجرا شدند.
مقدار CPU و حافظه برای دو پاد وب تعریف شد.
از داخل BusyBox به هر دو Nginx با IP مستقیم متصل شدیم.
حذف پاد معمولی و بازیابی دستی آن آزمایش شد.
حذف Namespace توسعه روی Namespace عملیاتی اثر نداشت.
یادگیری کلیدی: Namespace محدوده نام‌گذاری و سازمان‌دهی منابع است؛ Pod واحد اجرای کانتینر است. بدون کنترلر، Pod حذف‌شده خودکار جایگزین نمی‌شود. بدون Service نیز می‌توان با IP پاد ارتباط گرفت، ولی آن IP پایدار نیست.
